# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Pnakotic is a redirect-chain / malvertising scanner (proof of concept). A URL is submitted to a FastAPI service, a Celery worker opens it in headless Chromium (Playwright) under a chosen browser profile, records every redirect hop, runs regex static analysis on the landing page, takes a screenshot, and assigns a heuristic `malicious_score` (0–1). A React dashboard (`frontend/`) submits scans and visualizes the chain.

A second mode, the **site survey**, takes a domain, loads a handful of its pages as several visitor types and reports where a compromise lives (page or script URL plus a code snippet). It is a crawl, roll-up and report around the same per-load pipeline; the single-URL probe is unchanged. See "Site survey" below. It was called "site check" until it was renamed to stay clear of Sucuri SiteCheck; only the prose and UI labels changed, so code identifiers (`/site-scan`, `kind="site"`, the `site` queue, `run_site_scan_worker`, `site_*.py`, Python docstrings) still say `site`/"site check".

## Commands

Backend (run from this directory — the repo root):

```bash
pip install -r requirements-dev.txt && playwright install chromium
python3 -m pytest                                   # all tests
python3 -m pytest tests/test_engine.py::test_scoring_ip_landing   # single test
python3 -m pytest -k "scoring or static or artifact"              # offline unit tests only
```

Full stack (Postgres, Redis, API on :8000, 2 workers, frontend on :5173):

```bash
docker compose up --build
```

The `api` container runs `alembic -c pnakotic/alembic.ini upgrade head` before uvicorn. Running the API or worker outside Docker must be done from the **parent** directory (see import path below), e.g. `uvicorn pnakotic.src.api.main:app` and `celery -A pnakotic.src.workers.celery_app worker`, with `DATABASE_URL` / `REDIS_URL` set (the defaults point at the compose hostnames `db` / `localhost`). A local worker must consume both queues to run site surveys too: `celery -A pnakotic.src.workers.celery_app worker -Q celery,site --loglevel=info` (or a second worker with `-Q site`). Compose splits them: `worker` runs `-Q celery`, `site-worker` runs `-Q site --concurrency 1`.

Frontend (`frontend/`): `npm run dev`, `npm run build` (runs `tsc` then `vite build` — this is the only type check; there is no lint or test script). API base URL comes from `VITE_API_BASE` (default `http://localhost:8000`), baked in at build time.

## Import path (important)

All code is imported as the package `pnakotic.src...`, so this directory must be named `pnakotic` and its **parent** must be on `sys.path`. `conftest.py` and `alembic/env.py` insert the parent; the Dockerfile copies the repo to `/app/pnakotic`. Inside `src/`, modules use relative imports, except `workers/celery_app.py`, which imports `pnakotic.src...` absolutely inside the task body. Tests import inside each test function.

## Architecture

Request flow (URL probe; the site survey's flow is under "Site survey" below):

1. `POST /scan` (`src/api/main.py`) validates the URL (input with no scheme gets `https://`, an explicit scheme is lowercased and must be http or https, plus `_assert_public_host`, which resolves the host and rejects any non-public address as an early 400), writes a `ScanJob` row with status `queued`, then calls `run_scan_worker.delay(...)`. If dispatch fails, the job is marked `failed` and the endpoint returns 503.
2. `run_scan_worker` (`src/workers/celery_app.py`) sets the job to `running` and refreshes `updated_at` (also on re-delivery; that column is the sweeper's clock), runs the async `PnakoticEngine.scan()` in a fresh event loop, replaces any existing result row, writes a DB `ScanResult`, and sets `completed` (or `failed` with a truncated error). Celery uses `task_acks_late` + `task_reject_on_worker_lost`, so tasks **must stay idempotent**: completed jobs are skipped, and stale result rows are deleted before insert.
3. `PnakoticEngine.scan()` (`src/scanner/engine.py`) runs `_scan_in_context()` once per profile (see Profile comparison below); each run applies a `BrowserProfile` (`profiles.py`: `default`, `mobile-ios`, `mobile-android`, `search-clicker`, `facebook-android`, `googlebot`). `{chrome}` in a profile's UA is filled from `browser.version` (`user_agent_for`), and `Emulation.setUserAgentOverride` sets matching client hints (`user_agent_metadata`); without that, `sec-ch-ua` names `HeadlessChrome` whatever the UA string says. The API rejects unknown profile names (422). It records two kinds of main-frame redirect (not subresources or iframes): each navigation 3xx as an `http_3xx` hop (`on_resp`), and each client-side navigation reported by CDP `Page.frameRequestedNavigation` (`scriptInitiated` → `js_location`, `metaTagRefresh`/`httpHeaderRefresh` → `meta_refresh`, anything else → informational `client_navigation`; mapping in `NAVIGATION_MECHANISMS`). A client-side hop's `url` is the page that issued it and the destination is `evidence["to"]`. Both kinds go through `note_redirect()`, which stops the page at `max_hops`. Navigation is `goto(wait_until="load")` followed by a bounded `networkidle` settle (`SETTLE_MS`); then `final_url`, `page.content()`, `StaticAnalyst`, and the screenshot (with `SCREENSHOT_TIMEOUT_MS` and a CDP `Page.captureScreenshot` fallback) each run in their own step, so a timeout in one does not skip the others. Only Playwright errors are caught on that path; anything else (including Celery's `SoftTimeLimitExceeded`) propagates so the worker marks the job `failed`. Each static signature becomes a hop with the mechanism from `SIGNATURE_MECHANISMS`; the analyzer caps its input at `MAX_CONTENT_CHARS` and its regexes use bounded quantifiers (attacker-controlled input). Popups are blocked by `--block-new-web-contents`, but CDP `Page.windowOpen` still fires for each attempt, which becomes a `popup_open` hop (`evidence`: `to`, `trigger` load|click, `user_gesture`; capped at `MAX_POPUP_HOPS`). Step 4, after the screenshot, is the click probe: `NEUTRAL_POINT_JS` picks a point that is not a link or control (in the page's CSS pixels, the space `page.mouse.click` uses), `phase` switches to `"click"` before the click, and for `CLICK_SETTLE_MS` any main-frame navigation becomes a `click_hijack` hop and 3xx responses are ignored, so nothing after the click moves `final_url`. It then calls `PnakoticScorer.score()`; before that the engine sets `metadata["page_signals"]` (title, password-input count, form count, main-frame content type, whether the landing was Chrome's `chrome-error://` page), and skips `StaticAnalyst` for an error page or a non-HTML landing document (recording `metadata["navigation_failed"]` for the former). The scorer's brand (`BRANDS`), throwaway-hosting (`THROWAWAY_HOSTING`) and TLD lists are module constants in `scorer.py`.
4. A background sweeper in the API `lifespan` (`sweep_stale_jobs`) marks as `failed` any job stuck in `running` longer than `STUCK_JOB_TIMEOUT_MINUTES` (default 15) or in `queued` longer than `QUEUED_JOB_TIMEOUT_MINUTES` (default 60). Each rule is a single conditional UPDATE, so it can't overwrite a job a worker just picked up.

Endpoints that touch the DB or the broker are plain `def`, so FastAPI runs them in its threadpool. `POST /scan` is `async` only for the DNS check, and runs its DB/dispatch part through `run_in_threadpool`. Keep blocking calls out of `async def` handlers.

Key concepts that span files:

- **Egress guard (SSRF).** `src/scanner/netguard.py` is the single policy: a host is allowed only if every address it resolves to is globally routable. The API uses it for the early 400. The engine enforces it in two layers. (1) `src/scanner/egress_proxy.py` is a per-scan local SOCKS5 proxy; the browser is launched with it at launch level, so Playwright also maps every hostname to NOTFOUND in Chromium's resolver and the proxy receives names, resolves them once, checks every address and connects to one of those checked addresses (pinned, so DNS rebinding is closed). This is the layer that covers WebSockets, SharedWorkers and anything else CDP can't see. (2) `EgressGuard` in `engine.py` keeps CDP `Fetch` interception for precise per-URL blocking and `ERR_BLOCKED_BY_CLIENT` errors. Popups are disabled (`--block-new-web-contents`), service workers are blocked, and WebRTC's direct UDP paths are disabled by flag. Blocked hosts from both layers are merged into `metadata["blocked_hosts"]` (only after a block actually happened) and an unweighted scoring finding. The browser launches with `chromium_sandbox=True` via `launch_options()`, which also reads `BROWSER_CHANNEL` (`chrome` in the Docker image, so scans run in Google Chrome stable, which gets security builds on Chrome's schedule; empty locally for the bundled Chromium, which lags stable). `playwright` is pinned in `requirements.txt`; the Dockerfile's `BROWSER_CHANNEL` build arg must be `chromium` on arm64, where Chrome has no Linux build. Tests that scan a local server must pass `host_allowed=` to `PnakoticEngine`; both layers use the same injected policy.
- **Malvertising detection beyond redirects.** `src/scanner/behavior.py` installs page-side hooks (init script + a randomly named, self-removing Playwright binding) before any page script runs, and records dialogs and downloads from Playwright (dialogs are always dismissed, downloads always cancelled). Events become `page_behavior` hops whose JSON evidence carries the event id and `trigger` (`load`, or `click` once the click probe starts; the scorer words findings by it). `window.open` is deliberately not hooked: popups come from CDP as `popup_open`, which the page can't see or forge. `src/scanner/yara_scan.py` compiles the rules under `YARA_RULES_DIR` once per process (off when unset; rules are private and never committed, tests write synthetic ones) and matches the rendered HTML, subframes and loaded script bodies after the context closes (`yara_match` hops); it uses yara-python (libyara); yara-x was tried, but its scans died with SIGKILL in a sandboxed macOS dev session. Neither mechanism may join `REDIRECT_MECHANISMS`, and the frontend marks them on an existing depth (`MARK_ONLY` in `RedirectChain.tsx`) instead of adding one. `src/scanner/eval_capture.py` captures code the page builds at runtime (`eval`, `new Function`, an inserted inline `<script>`, a `data:` or `blob:` script) through CDP `Debugger.scriptParsed` on the load's CDP session, in every mode: `EvalCapture` keeps up to 20 stages (200 000 characters each, 2 000 000 bytes in all) and the engine stores `metadata["eval_stages"]` (`caller`, `caller_line`, `length`, `markers`, a `context` snippet, `yara_matched`, `oversized`; never the body). Overflow is counted, not silent: `eval_stages_dropped`, and `eval_stages_repeated` for the same code seen again (same CDP `hash`, which takes no slot). Once the 20 slots are full a stage with obfuscator markers replaces one without; at most 100 sources are read per load and a script over 2 000 000 characters is recorded without source (`oversized`, no YARA buffer, no markers). A stage is a script with no URL, one with a `data:`/`blob:` URL, or one that renamed itself with a `//# sourceURL=` comment (`caller` is the top frame of the stack that built it, `""` when a timer or promise ran it and there is no stack). Playwright injects URL-less scripts too (init scripts, the utility script, every `evaluate` payload), so those are excluded by content alone: anything in an isolated world, and anything whose CDP `hash` was parsed before the capture sealed (it replays the blank page's init scripts and runs a warm-up of every main-world `evaluate` the engine makes and one behavior-hook binding round trip, so Playwright's binding delivery script is known too; a new engine `evaluate`, or a new recorder with its own binding, must be added to that warm-up). A stack or a harness caller never excuses a script, because a page can copy Playwright's utility script or point `String` at `eval` and let a hook call it. Setting `Debugger.setSkipAllPauses` did not keep a `debugger;` statement from pausing the page in Chromium 148, so the capture also deactivates breakpoints and resumes any pause. Stages are YARA buffers of source `eval` (after the page and frame documents, before the script bodies) that `scan_buffers` always names `script.js`, so JavaScript rules that test the extension apply; `obfuscator_markers` runs over each stage, and a stage with markers adds an unweighted scoring finding (no `WEIGHTS` change). All page-supplied data is bounded (ids whitelisted, strings truncated, counts and bytes capped, YARA timeouts and a per-page budget).
- **Decisive vs. additive scoring.** `PnakoticScorer.score()` still adds `WEIGHTS`, but `_decisive()` / `_yara_decisive()` can force 1.0 (ClickFix clipboard command, executable drive-by download, two browser-lock behaviors, a production YARA rule of severity >= 4); those strings lead `scoring_findings` and are stored in `decisive_findings`. Existing weights and their exact-sum tests are unchanged.
- **Profile comparison (cloaking).** `scan(url, profile, compare=True)` runs `_scan_in_context()` for every profile in parallel contexts of one browser (one shared egress proxy), scores each, then `PnakoticScorer.combine()` folds them: job score = worst profile, findings from other profiles are prefixed `[profile]`, and differing landing apexes are cloaking (0.35, or decisive when any profile's own page is >= 0.4). The requested profile's hops stay the job's hops; `metadata["variants"]` lists every profile (requested first, own score). Comparison screenshots go to `profiles/<name>/` so the dashboard's "newest PNG under screenshots/" pick stays the requested profile's. `POST /scan` has `compare_profiles` (default true); the Celery task's `compare` parameter defaults to false so older queued messages keep their meaning. A comparison profile's browser error is recorded, not fatal; any other exception still propagates.
- **Two different `ScanResult` classes.** `src/scanner/models.py` has the Pydantic engine output; `src/database/models.py` has the SQLAlchemy row. The worker maps one onto the other. Hops, artifact manifest, scoring findings, `raw_error` and `redirect_loop` are stored in the DB row's `metadata_json` (JSONB, Postgres-only; named that way to avoid clashing with `Base.metadata`).
- **Redirect vs. passive mechanisms.** `REDIRECT_MECHANISMS = {http_3xx, meta_refresh, js_location}` are redirects the browser actually performed. Only these make `is_redirect_chain_detected` true and count toward the scorer's `deep_chain` and "high-value landing after redirect" rules. Regex hits on the landing page are weaker "code present but did not fire" signals: `meta_refresh_code` (0.1) and `js_location_code` (0.15), each applied once. `js_obfuscation` hops (`atob`, `String.fromCharCode`) score once but aren't redirects, and only at 0.4 next to a cross-site redirect, a brand-name hostname or a credential form (otherwise `js_obfuscated_only`, 0.1). Observed `js_location` / `meta_refresh` hops are scored only when they cross registrable domains (`_hop_crosses_sites`, unknown destination counts as crossing); a same-site one is an unweighted finding. The engine records a client-side navigation to the page's own URL (fragment ignored) as an informational `client_navigation` with `"self": true` (still counted by `note_redirect()` so reload loops stop). A `<meta refresh>` without `url=` and base64 inside `data:` URIs are ignored by the analyzer. `popup_open` and `click_hijack` are not redirects either: they score once each (`popup_cross_site` 0.3, `click_hijack` 0.4), and only when the destination is another site (`_cross_site_targets`). `client_navigation` (form submit, anchor click) and `static_analysis` hops (for example `b64_payload`, `content_truncated`) are informational. `frontend/src/lib/format.ts` mirrors `REDIRECT_MECHANISMS` and labels every mechanism in `MECHANISM_LABELS`, so adding a mechanism means updating both. Adding a new signature means updating `StaticAnalyst.SIGNATURES` and `SIGNATURE_MECHANISMS`; if it should score, also update the scorer's `WEIGHTS`. Every load (probe or site) also runs a `ScriptCollector` and a `ScriptTracer` and stores `metadata["injections"]` (`find_injections`; no served HTML in a probe, so inline injections carry no block) and, when any, `metadata["flagged_scripts"]`; the scorer's `_script_support` adds `flagged_script` (0.4, once) and `obfuscated_injection` (0.4, once: an inline or same-registrable-domain loader with `markers` or `body_markers`; a third party's loader does not count). Neither is stored in the URL probe's `metadata_json`; only the finding strings are.
- **Artifacts.** The root is `ARTIFACTS_DIR` (default `./artifacts`, relative to the cwd; `/app/artifacts` is a shared volume between API and worker in compose). `resolve_task_folder()` is the single place a task ID becomes a path: it validates the ID (alphanumerics, `-` and `_`) and blocks traversal. `task_folder_for()` (API) and `ArtifactManager` (engine) both go through it. The worker doesn't pass a folder; the engine derives `<root>/<job_id>` itself. The task's optional fourth `task_folder` argument is ignored and kept only so messages from older APIs still run. Manifest `rel_path`s are served by `GET /tasks/{id}/artifacts/{path}`.
- **API response shape.** `/tasks` and `/tasks/{id}/results` share `serialize_result()` in `main.py` (`final_url`, `malicious_score`, `is_redirect_chain_detected`, `hops`, `artifacts`, `findings`, `decisive`, `variants`, `cloaking`, `yara`, `raw_error`). New result data must be added in three places or it silently disappears: the worker's `metadata_json` dict (`run_scan_worker` or `run_site_scan_worker`), `serialize_result()`, and `ScanResultData` in `api.ts`. That now covers `kind` (`url` | `site`, in `metadata_json` and in each `/tasks` job), `site` (the report) and `cleanup_url` (read from `CLEANUP_URL` in `serialize_result()`, site results only). `frontend/src/lib/api.ts` (`ScanResultData`) mirrors it by hand, so change both together. `/tasks` eager-loads results with `joinedload` (one query).
- **Schema.** Alembic (`alembic/versions/`) is the source of truth. `init_db()` (`create_all`) also runs at API startup and in the sweeper as a convenience, so a model change still needs a matching migration.

## Site survey

`POST /site-scan` (`src/api/main.py`) turns the input into `https://<host>[:port]/` with `normalize_site_input()` (422 on bad input), runs `_assert_public_host` (400), writes a `ScanJob` with `kind="site"` (the `scan_jobs.kind` column, Alembic `0002`, default `url`, so old rows and queued messages keep meaning `url`) and calls `run_site_scan_worker.delay(job_id, homepage_url)` (503 and a failed job if dispatch fails). `run_site_scan_worker` (`pnakotic.site_scan`, soft 240 s / hard 300 s set on the task) follows `run_scan_worker`'s lifecycle and idempotency exactly, runs `SiteScanner(engine).scan()`, and stores one `ScanResult` row: `final_url` is the homepage's default landing, `malicious_score` the worst load's score, and `metadata_json` has `kind: "site"`, `site` (the report), `artifact_manifest`, `raw_error`, `blocked_hosts`. The sweeper is unchanged.

**Queues.** `celery_app.conf.task_routes` sends `pnakotic.site_scan` to the `site` queue; everything else stays on `celery`. A site survey holds a worker for up to 150-300 s and opens up to 6 contexts, so URL probes must not wait behind it. A worker started without `-Q` consumes only `celery`, so site surveys wait for a worker that lists `site`; don't add `site` to the `-Q` of the scaled `worker` service.

**Flow (`src/scanner/site_engine.py`, `SiteScanner`).** `engine.browser_session()` (the browser plus egress proxy that `scan()` also uses) is opened once for the whole check, and every load is `engine._scan_in_context(..., options=LoadOptions(site=True, ...))` in a fresh context under a semaphore of 6.

1. Stage 1: the homepage in `default`, `mobile-ios`, `googlebot` and `search-clicker`. If `default` fails with `net::ERR_` over https, all four are redone over http (their screenshots are deleted first).
2. The site host: `resolve_site_host()` follows a homepage redirect only within one registrable domain (`site_identity.py`, public-suffix data bundled with `tldextract`, no network and no cache directory). A landing on another domain keeps the entered host as the site and becomes an `offsite_homepage` finding.
3. Links come from the first homepage load, in profile order, whose landing is on the site (`on_site()`: the host or its www twin). `pick_pages()` (`page_picker.py`) takes up to 5: a post, a page, an archive, a contact page, then distinct first path segments, then document order. Each URL must pass `engine.host_allowed`. If no homepage load stayed on the site nothing is crawled. A 404 probe, `/pnakotic-<12 hex>/`, is appended.
4. Stage 2: every picked page and the probe in `default`, `mobile-ios` and `googlebot`. Homepage `default` is a full-page screenshot, every other load a viewport one, written to `pages/<n>/<profile>/`.
5. Budget: 150 s from the start of stage 1. After that no load starts, loads still running get 10 s, then are cancelled and recorded as `not_checked: budget`. Only Playwright errors (`BROWSER_ERRORS`) are caught per load; anything else, including `SoftTimeLimitExceeded`, propagates and fails the job.
6. Each load is scored with `scorer.score(result, site_host=...)`, then each page's other profiles are folded into its default load with `combine()` (which accepts any subset of profiles). `build_report()` rolls it all up.

**`LoadOptions(site=True)`** (`engine.py`) is how `_scan_in_context()` serves the site survey; without options it is the URL probe's load. `shot_dir` and `full_page` override where and how the screenshot is taken; `site=True` also reads the served main-frame body (`_served_body`, capped), extracts links from the rendered DOM, and adds to `result.metadata`: `main_status`, `served_bytes`, `links`, `script_requests` and `challenge` (script bodies, the `ScriptTracer` and `injections` are kept in every load since the URL probe scores them too) (plus `challenge_vendor`, `cloudflare` | `ddos-guard` | `incapsula` | null, when it is one). YARA then scans the served HTML as source `served` first and returns one match per (rule, buffer) (`scan_buffers(per_buffer=True)`), each with a `context` snippet and `offset`; the URL probe keeps one finding per rule per page. A load's own egress-guard blocks are moved from `guard_blocked_hosts` into the site's `blocked_hosts` by the site engine. Whenever script bodies are collected (YARA on, or site mode), `metadata["flagged_scripts"]` lists the script responses a CDN refused as malware (`ScriptCollector.flagged`: `url`, `status`, `reason`). Such a refusal is an HTML page in a script's place, and for a cross-origin script Chromium's opaque-response blocking drops it before any response event (`net::ERR_BLOCKED_BY_ORB`; CDP `Fetch` at the response stage doesn't see it either), so the collector fetches those few URLs once more through `context.request` (same UA and cookies, same launch-level SOCKS proxy, so the egress policy still applies), bounded by `MAX_PROBES`, `PROBE_TIMEOUT_MS` and `PROBE_MAX_BYTES`. This came from a field case (abacashi.com, 2026-11-09): an injected campaign page built `https://r1.fo/donation` with `String.fromCharCode`, the served HTML never named the host, the payload was obfuscator.io output matching an exploratory YARA rule, and Cloudflare had put its malware interstitial on it, so the request left no response at all.

**Site-mode scoring must not touch `WEIGHTS`.** The exact-sum scorer tests and the URL probe's results depend on them. `PnakoticScorer.score(result, site_host=None)` takes the site host; when the landing is `on_site()` it skips the `IDENTITY_SIGNALS` tuple in `scorer.py`: `suspicious_tld`, `watch_tld`, `throwaway_hosting`, `brand_in_hostname`, `brand_in_title`, `js_obfuscated_only` and `ip_landing`. An on-site brand-like host also does not lift `atob` to the strong obfuscation weight. An off-site landing is scored in full. Add a new identity-style weight to `IDENTITY_SIGNALS`, not a second table, and keep `site_host=None` meaning "unchanged".

**Verdict and severity.** A finding is `compromised` when it is decisive under the existing rules (production YARA rule of severity 4 or higher, a decisive behaviour, decisive cloaking) and `suspicious` for any other YARA match, an obfuscated injector, an off-site homepage, non-decisive cloaking whose page's combined (post-`combine()`) score is 0.4 or more (a `cloaking` finding naming where the sent-away visitors land; on the homepage with an off-site domain it is folded into the `offsite_homepage` finding), or a page whose own score is 0.4 or more. An injection is a finding only when code shows obfuscator markers: either the injecting code (`markers`, the existing `injection` message) or the script it loaded (`body_markers`, computed by `find_injections` from the kept script body; the `injection_obfuscated` message, keyed by the requested URL). A plain loader fetching a plain script is nothing. A script the CDN refused as malware (`metadata["flagged_scripts"]`, see below) is a `suspicious` `flagged_script` finding at the script URL (`location_kind: script`, `loaded_by` the page and the code that loaded it, which is then not reported again as an injection); only reasons in `FLAGGED_VENDORS` count. A load that ended off the site (`ended_off_site()`) is the other site's page: its YARA matches sit at the landing URL (or script URL) with `origin` null and `details.offsite: true`, its injections are skipped, and it adds nothing to External scripts. The 404 probe (highest-index page whose path starts with `/pnakotic-`) carries `probe: true` on its `checked.pages` entry and its blocks, shown as "Your 'page not found' page". `site_verdict()` gives Compromised, Suspicious, Couldn't check (homepage default load not checked), Partly checked (a homepage load, or over half the other loads, not checked) or Clean ("Clean (no malware rules loaded)" without YARA); unchecked loads must never read as Clean. When a CDN bot check kept any load out, the report's `challenge` (`challenge_summary()`: vendor, loads blocked, of how many, whether the homepage was one) drives an alert in `SiteReport.tsx` that says it is not a sign of a hack and how to let a re-check through; the vendor is kept only if it is one of `challenge.VENDORS`. The cleanup link (`CLEANUP_URL`, default `https://elderward.space.fast`) is shown for Compromised and Suspicious.

**Page-supplied data.** Everything a site load returns is attacker input. Every URL stored in a report is cut to 300 characters; blocks (50), findings per block (20), findings in all (200, compromised first, `cap_findings()`; the rest in `findings_more_total`, and blocks it empties in `blocks_more`), pages per finding (20), external-script hosts (100) and URLs (500), blocked hosts (100) and script records (200 per load, 50 injections) are capped, and the overflow is counted. Report data holds snippets only, never page or script bodies. `site_findings.py` and `site_report.py` are pure (no I/O).

**Frontend.** `ScanForm` has a kind switch (Site survey, the default, and URL probe). `SiteReport.tsx` renders the report from `ScanResultData.site` (layout A: finding blocks by location, External scripts, What was checked); `ScanList` and `SelectedScan` branch on `task.kind` and show the site verdict, not a score. The report body is plain language; the ritual vocabulary stays in the chrome and form errors.

## Tests

`tests/test_netguard.py` unit-tests the egress policy. `tests/test_static_analyzer.py` covers the analyzer's regexes, the 2 MB input cap and two adversarial inputs under a 1 s budget. `tests/test_api.py` covers the endpoints, sweeper and worker against a temporary SQLite DB: its `db` fixture patches `SessionLocal` in both `main` and `database.session`, and compiles JSONB as JSON. The worker tests swap in a fake engine, so no Postgres, Redis or browser is needed. `tests/test_engine.py` contains offline unit tests (scorer weights, static-analyzer regexes, artifact safety), engine tests against a local `127.0.0.1` server (the `local_site` fixture), and two live tests that scan the real `google.com`. `tests/test_popups_personas.py` covers popup capture, the click probe, click hijacks, the persona headers and client hints, against its own `popup_site` server. Browser tests are skipped automatically when Chromium can't launch. The google.com tests write screenshots to `./artifacts/test-job/` under the cwd. Scorer tests assert exact weight sums, so changing `WEIGHTS` means updating them. The site survey has its own files: `tests/test_site_identity.py`, `test_site_findings.py`, `test_site_report.py` and `test_site_engine.py` (pure or fake-engine, no browser), and `tests/test_site_load.py` (browser tests of `LoadOptions(site=True)` against a local server, skipped without Chromium). `tests/_support.py` holds the shared browser fixtures.

## Frontend design

The dashboard follows a deliberate design system documented in `.taste-skill/notes.md`. It uses the "data-terminal" app-screen style with an abyssal green-black ground and one phosphor-teal accent. Public Sans is used for text, IBM Plex Mono for every figure, ID and URL, and Chakra Petch for the wordmark only. The type scale has a 12px floor for meta (timestamps, IDs, axis labels), 14px body and cells, 15px semibold ink for section labels inside cards ("Descent", "Findings", "What was checked"), 18–20px card titles, 24–28px for the selected probe's site name, 28px KPI values and a 24px score; the probe totals strip sits at the bottom of the page (it matters for long-running monitoring, not a one-off check); the h1 is the lockup of the 44px mark, the 30px "PNAKOTIC" wordmark and "Observatory" beside it. `--muted` (~10.5:1) and `--faint` (~7:1) are kept far apart, so promote what carries the answer to `text-ink` or `text-muted` and leave `text-faint` for meta. Selection is shown as a 1px accent line, with no glow, glass or entrance animations. The one exception is `ProbeRitual.tsx`, the canvas scene shown while a probe is queued or running (glowing sigil, hash rain made from the probe's own SHA-256 digests; a still frame under reduced motion). Colors are CSS variables in `src/index.css`, exposed as Tailwind tokens (`ground`, `surface`, `raised`, `ink`, `accent`, `line`, …) in `tailwind.config.js`; use the tokens, not raw colors. Each token is wrapped in `color-mix(... <alpha-value> ...)` so opacity modifiers like `bg-accent/60` compile; a plain `var(--x)` token would silently drop them. Hop counts in the UI count only redirect mechanisms (`redirectCount` in `src/lib/format.ts`, mirroring `REDIRECT_MECHANISMS`). The vocabulary is "ritual/abyss": the screen is the "Observatory", a scan is a "probe" in every label and message, the chain is the "Descent" (each node a depth), and form errors open with a phrase in the voice ("The gate is sealed.") followed by the API's real reason. Data labels and verdicts (Benign / Watch / Suspicious / Malicious) stay literal. Keys: `/` focuses the URL prompt (`#probe-target`), j / k move through the probe list. The mark (`Mark.tsx`, `public/favicon.svg`) is the Pnakotic sigil: a point-down pentagon holding a redirect path from a hollow origin node to a solid landing node. The root `SKILL.md` is a vendored copy of the `design-taste-frontend` skill used for that redesign, not project documentation.
